# Cleaned-source duplicate-key audit

The v5 inventory identified duplicate normalized (YEAR, STATE, UNIT_NAME) keys in five cleaned 2001–2012 files. These outputs compare every non-key field. Generated pipeline metadata (source row IDs, quality flags and unit labels) is reported separately from offence payload values.

The integration notebook assigns `DUPLICATE_KEY_REVIEW`, classifies exact whole-row duplicates separately from conflicting offense payloads, then assigns `SOURCE_QUALITY_STATUS=DUPLICATE_KEY` to duplicate keys and admits only `VALID` ordinary district/reporting rows into the core stage. Consequently, all seven affected key groups listed here are absent from their corresponding core files. This is an explicit exclusion rule in the notebook, not a crime-count aggregation rule.

Two key groups have conflicting offence payloads: Jammu & Kashmir / RAILWAYS / 2010 in IPC and women files. Both are categorized as special units and excluded. The rows have distinct source row identifiers but no further railway-unit identifiers; why the counts differ cannot be resolved from available files. Five groups have identical offense payloads and differ only in source-row/provenance identifiers: duplicated Anantnag 2001 in SC and ST, and Nagaland TOTAL 2005 in SC, ST and children. `TOTAL` is an aggregate, while Anantnag is an ordinary district name; its duplicated SC/ST records are both excluded by the duplicate-quality rule. Whether the duplicate source rows arose in NCRB extraction or another upstream process is unverified because original raw files are absent.

The canonical integrated target/model input has unique district-year keys. The forecast target and predictors use IPC sources only; these duplicate groups do not introduce duplicate canonical model rows. However, excluding Anantnag 2001 removes the affected SC/ST source observations from their core family tables. No rule was invented to keep one or aggregate the duplicates. Raw/cleaned/core files were not modified.
